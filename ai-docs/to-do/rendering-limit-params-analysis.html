Cocos 4.x 渲染模块极限参数分析

骨骼动画 · BlendShape · 光源控制 · Uniform/UBO 容量（精简通俗版）

这份报告在说什么？ 它把 Cocos 4.x 引擎里四个最常"卡上限"的渲染功能——骨骼动画、面部/形变（BlendShape）、灯光、Uniform 缓冲区——的最大容量、为什么会卡、源码在哪、怎么突破讲清楚。所有结论都来自仓库源码，不是猜测。

前置结论（先看这个）

  • 版本：本仓库是 Cocos Creator 4.x，不是任务最初提到的 3.x。
  • 后端：原生渲染后端是 vulkan / wgpu / metal / gles2 / gles3，已经没有 D3D12 后端。
  • 一句话原理：所有上限最终都取决于设备的「能力表」DeviceCaps。引擎对关节 / 形变 / 灯光都用了同一招——「小容量走 GPU 快路径，超限就自动降级」，所以大多数情况下你"改个模型"就能继续用，真正的硬墙只剩显卡的显存与带宽。

极限参数总览表

模块默认 / 推导上限限制类型最关键的宏 / 变量
骨骼动画 uniform 关节数 = floor((顶点uniform向量数 − 预留)/3)，硬上限 256；纹理通道 256 关节 硬件+软件 CC_JOINT_UNIFORM_CAPACITY、UBOSkinning

① 骨骼动画（Skeleton）

极限参数

参数默认 / 上限说明
uniform 关节容量30（历史兼容默认）可被运行时覆盖
运行时关节数floor((maxVertexUniformVectors − 保留量)/3)，封顶 256受显卡顶点 uniform 容量约束
每关节占用3 × vec4 = 48 字节骨骼矩阵 mat3×4
关节纹理容量宽 256 × 高 3 → 256 关节超限时自动切换
顶点影响数固定 4每顶点最多受 4 根骨骼影响

底层原理（通俗版）

骨骼动画要把每根骨骼的"变换矩阵"送给 GPU。有两种送法：

  • 塞进 Uniform（直接变量）：把矩阵写进一个叫 cc_joints 的 uniform 数组。但顶点着色器里能用的 uniform 总量是有限的，而且这个总量被"全局相机 UBO + 阴影 UBO + 蒙皮 UBO"一起瓜分。所以骨骼越多，占的份额越大——这就是关节数的天花板来源。
  • 塞进纹理（间接查表）：把矩阵编码成一张浮点纹理，着色器用顶点坐标去"查表"取矩阵。这样就不占 uniform 额度了，改成受"顶点纹理单元数"和"纹理尺寸"约束。

当骨骼数超过 uniform 容量时，引擎会自动从第一种切换到第二种。这就是为什么你给它一个 100 骨骼的模型，它不会报错——只是悄悄换成纹理方案。

关键源码定位

  • 容量常量与运行时计算：cocos/rendering/define.ts（JOINT_UNIFORM_CAPACITY L600、UBOSkinning L651、localDescriptorSetLayout_ResizeMaxJoints L688）
  • uniform 关节推导两处：cocos/root.ts:809 与 cocos/rendering/custom/web-program-library.ts:914（两处公式略有差异）
  • 自动降级判定：cocos/3d/models/skinning-model.ts:146（_realTimeTextureMode = true）
  • GLSL 采样：editor/assets/chunks/builtin/uniforms/cc-skinning.chunk、.../functionalities/skinning-animation-lbs.chunk、.../skinning-animation-dqs.chunk

怎么突破

  • 无需改代码：超过 uniform 容量时引擎自动掉到关节纹理，最多 256 骨骼。
  • 想要更多：调大 RealTimeJointTexture.WIDTH（默认 256），并同步修改 shader 里写死的 / 256.0、/ 1024.0 除数。
  • 提高 uniform 关节数：主动调 localDescriptorSetLayout_ResizeMaxJoints(n)，但天花板是 maxVertexUniformVectors，还要给全局 UBO 留空间。
  • 超 256：改用多张纹理 / 纹理数组 / 存储缓冲（SSBO），或对远处模型用 LOD 减骨骼。

② BlendShape 形变（Morph）

极限参数

参数默认 / 上限说明
GPU 形变目标数60权重 UBO 固定 15 个 vec4 = 60 个权重
超过 60 个自动回退 CPU 计算无硬性上限，但很慢
位移纹理格式RGBA32F（支持浮点）或 RGBA8888（打包）取决于硬件
纹理容量顶点数 × 目标数 ≤ maxTextureSize²硬件限制

底层原理（通俗版）

BlendShape 就是"把每个顶点的偏移量按权重叠加上去"。每个形变目标（target）的偏移量存进一张纹理，顶点着色器按 顶点序号 × 目标序号 去取，再乘上权重累加。

权重表的大小是固定的：只有 15 个 vec4（共 60 个浮点），所以GPU 方案最多支持 60 个形变目标。一旦超过，引擎就放弃 GPU，改在 CPU 上算好再上传——能继续用，但每帧 CPU 重算，开销随（顶点数 × 目标数）飙升。

⚠️ 源码里有个"假上限"：cc-morph.chunk 写着 CC_MORPH_TARGET_COUNT range([2, 8])，但运行时这个宏会被设成实际的 target 数量（可达 60）。那个 [2,8] 是老旧的编辑器提示，不代表真实上限——别被它骗了。

关键源码定位

  • 容量与路径选择：cocos/rendering/define.ts（UBOMorphEnum L694）、cocos/3d/assets/morph-rendering.ts:120（>60 切 CPU）
  • 位移纹理生成：cocos/3d/assets/morph-rendering.ts（GpuComputing L232、CpuComputing L347、createVec4TextureFactory L535）
  • GLSL：editor/assets/chunks/builtin/uniforms/cc-morph.chunk、.../functionalities/morph-animation.chunk

怎么突破

  • 无需改代码：>60 个目标自动走 CPU 路径。
  • 扩大 GPU 路径到 60+：三处同步改——MAX_MORPH_TARGET_COUNT、cc_displacementWeights 数组长度、以及 cc-morph.chunk 里 cc_displacementWeights[15] 的 15。
  • 纹理装不下：顶点数 × 目标数必须 ≤ maxTextureSize²；超限就拆子网格或把目标分块到多张纹理。
  • 性能优化：用预计算位移（CC_MORPH_PRECOMPUTED）把"逐目标循环"从顶点着色器移出。

③ 光源控制（Light）

极限参数

参数默认 / 上限说明
前向渲染每像素灯数1主光 1 盏，其余灯各自多画一遍
延迟/Cluster 每像素灯数10一次算出 10 盏
场景灯光总数无硬上限视锥剔除动态收集，光越多越卡
主方向光1 个存于 UBOCamera
可投影光上限maxReceived = 4可配置

底层原理（通俗版）

前向渲染的逻辑是：先画一遍主光，然后有几盏点/聚光灯，就把受影响的物体再画几遍——每盏灯多一次 draw call。着色器每次只处理 1 盏灯（LIGHTS_PER_PASS = 1），灯光数据通过"动态 UBO"按偏移切来切去。

因此灯光数量没有写死的上限，但需要渲染的物体数量会随灯数线性放大，这才是真正的瓶颈。延迟/Cluster 渲染则一次处理 10 盏（LIGHTS_PER_PASS = 10），draw 次数少很多。

关键源码定位

  • 灯光 UBO 与每 pass 灯数：cocos/rendering/define.ts（UBOForwardLightEnum L549、UBODeferredLight L596）
  • 叠加光队列：cocos/rendering/render-additive-light-queue.ts（_lightBufferCount L123、_updateUBOs L478）
  • 灯光收集：cocos/rendering/scene-culling.ts:53
  • 阴影上限：cocos/render-scene/scene/shadows.ts:330、cocos/scene-graph/scene-globals.ts:999
  • GLSL：editor/assets/chunks/builtin/uniforms/cc-forward-light.chunk

怎么突破

  • 减少 draw 数：换用延迟/Cluster 管线（LIGHTS_PER_PASS = 10）。
  • 前向下优化：缩小每光 UBO 对齐浪费、关闭不必要的阴影、把静态光烘进 lightmap。
  • 更多投影光：调大 ShadowsInfo.maxReceived（代价：阴影贴图内存与带宽线性增长）。
  • 海量动态光：开启 Cluster 光剔除（CC_ENABLE_CLUSTERED_LIGHT_CULLING）替代逐光 forward-add。

④ Uniform / UBO 容量

极限参数（设备能力表 DeviceCaps）

能力项典型值 / 保证最小值类型
maxVertexUniformVectorsVulkan: maxUniformBufferRange / 16；GLES3 最小 256；桌面 4096硬件
maxUniformBlockSizeVulkan: maxUniformBufferRange（最小 16 KB，桌面常 64 KB）硬件
maxUniformBufferBindingsWebGL1 写死 16；WebGPU 12硬件
uboOffsetAlignmentVulkan minUniformBufferOffsetAlignment（常见 256 B）硬件
maxVertexTextureUnitsGLES3 最小 16硬件

底层原理（通俗版）

GPU 给"全局变量（uniform）"留的内存很小——单个 UBO 在 Vulkan 下最少只有 16 KB，桌面显卡通常 64 KB。引擎把所有渲染数据（相机、光照、阴影、骨骼……）塞进几块 UBO，再通过三组 Descriptor Set（GLOBAL / MATERIAL / LOCAL）组织。

关键连锁反应：顶点着色器里的 uniform 总量 = 全局 UBO + 本地 UBO 共享。所以骨骼想多用一点 uniform，就得压缩其它 UBO 的空间——这就是为什么架构上把大数据（骨骼、形变、海量灯）尽量搬去纹理或存储缓冲（SSBO）。

引擎内置 UBO 尺寸清单

UBO构成尺寸
UBOGlobal5 × vec480 B
UBOCamera6 × mat4 + 13 × vec4592 B
UBOShadow2 × mat4 + 8 × vec4256 B
UBOCSM4 级级联阴影656 B
UBOLocal2 × mat4 + 6 × vec4224 B
UBOSkinning关节数 × 3 vec4默认 1440 B（最大 12.3 KB）
UBOMorph15 vec4 权重 + 1 信息256 B
UBOForwardLight5 × vec4 / 灯80 B / 灯

关键源码定位

  • 能力表定义：cocos/gfx/base/define.ts（DeviceCaps L747）
  • Vulkan 映射：native/cocos/renderer/gfx-vulkan/VKDevice.cpp:311-326
  • WebGL2 映射与 iOS 修正：cocos/gfx/webgl2/webgl2-device.ts:173-195

怎么突破

  • 对齐优化：uboOffsetAlignment 常是 256 B，动态 UBO（如灯光缓冲）按对齐后的 stride 分配，避免浪费。
  • 大数据搬出 uniform：骨骼、形变、Cluster 灯光改用纹理或存储缓冲 SSBO（上限达 128 MB 级），绕开 16~64 KB 的 UBO 限制。
  • 精简全局 UBO：减少全局成员，为蒙皮 UBO 腾出顶点 uniform 预算。
  • 移动端兜底：尊重引擎对 iOS/微信浏览器 256/512 顶点 uniform 的 clamp，必要时主动降级到关节纹理。

硬件限制 vs 软件限制 · 一句话总结

模块硬性硬件限制软件逻辑限制
骨骼动画顶点 uniform 向量数、顶点纹理单元、纹理尺寸uniform 关节数（256 封顶）、纹理宽 256、顶点影响 4
BlendShape纹理尺寸、浮点纹理支持GPU 60 目标、权重数组 15 vec4
光源每帧带宽（draw 数）、阴影贴图内存前向 1 灯/pass、延迟 10 灯/pass、maxReceived=4
Uniform/UBOUBO 16~64 KB、绑定数、对齐 256 BDescriptor Set 布局、各 UBO 固定成员

一句话记住： 关节超限 → 切纹理；形变超 60 → 切 CPU；灯光太多 → 用 Cluster 把多灯合一趟；而所有这些的"真正天花板"只有三样东西——显卡的 uniform 字节数、纹理尺寸 和 带宽。
